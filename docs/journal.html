Build journal

What was built, what it cost, and what had to be thrown away. Newest first.

How to read this

A running log of a design being built in public, including the parts that went backwards. Several entries record work that was later deleted: a zero-knowledge virtual machine, a recursive proof design, a payment-rail brand. Those entries stay. The measurements that killed them are the reason the current design looks the way it does.

2026-07-29 · latest

The signature left the money path

Two days ago this journal recorded a rule, written down before measuring: the one-time signature inside the payment circuit survives only if it proves more than 2× faster than doing without it. It measured 6.7× slower. Today the migration that rule demanded is done. No signature is made anywhere on the money path. Spending a coin now means proving, inside the payment proof itself, that you know the secret behind the coin's committed spend anchor — a check the circuit was already doing next to the signature. The signature was a second lock on a door that had two, and the slower lock is gone.

What deleting it bought, beyond speed: the sharpest operational hazard in the system went with it. Signing twice under a one-time key discloses the key — so losing wallet state at the wrong moment could cost a coin, and a sign-log, a replay-instead-of-resign discipline, and fund-critical slot bookkeeping all existed to prevent that. Proving twice reveals nothing. All of that machinery is demoted from protecting funds to caching work, and the circuit that verified the signature — about 4,700 lines, most of the proving time, nearly all of the 1,024-row table — is deleted, not retired-but-kept. One circuit remains.

The note itself got simpler for the same reason. Each coin used to commit to an owner public key that the anchor check made redundant: the key authorized nothing the anchor did not already authorize. It is dropped. A note is now 28 field elements instead of 36, and the whole payment — opening the input coin, deriving the spend marker, opening both outputs, balancing the amounts, and the authorization itself — fits in a 16-row table where the signature version needed 1,024. A complete hiding payment proves in about 0.02 seconds on 5 MB, an order of magnitude faster and ~23× less memory than the circuit it replaced.

The honest cost, and it is not small: zero-knowledge is now load-bearing for funds. The spending secret enters every payment proof as witness data, so a proof system that leaked its witness would leak the thing that moves the money. Before, hiding protected privacy; now it protects the coin. This is contained the same way the old hazard was: anchors are one-time per note, so the blast radius of any single leak is one note. And the assumption base did not grow — the proof system and the hashes were already load-bearing; what changed is that a second, independent lock no longer sits behind them.

How we convinced ourselves the rewrite is the same circuit, not a similar one: the mutation sweep. Before the change, we deleted each rule of the old circuit in turn and recorded which deletions the tests catch. After the change, the same sweep on the new circuit catches the identical pattern — same rules defended, same rules leaning on the shared hashing machinery that a structural test does not yet isolate. That inherited gap is stated on the benchmarks page rather than papered over: 7 of 16 rules are pinned by a test that fails if they vanish, and the other nine are byte-identical to swept-clean rules of the deleted circuit. Outside review still owns the question our tests cannot answer.

Two withdrawals, recorded as such. The iPhone numbers this site quoted — a third of a second per private payment — were measured on the deleted circuit, so they are off the benchmarks page until the signed app re-measures them on the real one; the laptop got ten times faster, so the phone's budget only improves, but a number we have not measured is not a number. And every address and test asset minted before today is invalid: the note format changed shape, and this was the one asset-invalidating break the campaign budgeted for, spent while every coin in existence is play money.

A payment crossed Signal's real servers

Until today, "a payment rides Signal" carried an asterisk: the end-to-end test ran through our own relay, because we had not put two real accounts on Signal's actual service. Today the asterisk came off. One wallet issued an asset on public signet, paid 300 units to another, and the sealed bundle — 214 KB, mostly zero-knowledge proof — travelled through Signal's production infrastructure between two real accounts, arriving in under a second. The recipient's phone shows it as an ordinary file attachment, because to Signal that is all it is.

The receiving wallet's first scan fetched it, verified the proof, found the issuance and the spend marker confirmed on signet, and accepted. Nothing was retried and nothing was nudged. The supply check ran off the recipient's own chain view: 1,000 issued, every record attested.

One thing went wrong, and it is worth recording because it looked exactly like a transport bug. The receiving daemon sat connected for half an hour while the phone showed the message delivered — because it had been started with a flag that quiets received messages on standard output, and in that mode it was not consuming its queue at all. Restarting it without the flag flushed everything instantly. The lesson is now in the runbook: a receiving daemon that logs envelopes is receiving; one that logs nothing is not a daemon with nothing to receive.

The run is recorded in demo/signal.md's ledger — which also lost its "Commit" column today, for the same reason the other two ledgers did: this repository keeps one always-amended commit, so a commit hash can never resolve. A content hash of the transport sources stands in its place.

You can now count the coins

The question we get more than any other is how anyone knows how many coins exist. Until this week the honest answer was: you ask the issuer, and you believe them. That is the answer every token on every chain gives, and it is not a good one.

Now creating coins costs a confirmed Bitcoin transaction. Issuing writes a small record into the blockchain that states the amount in the open, and a wallet refuses any coin whose creation is not there. So an issuer cannot mint quietly on the side: unpublished coins are worthless to everybody, including them. Adding up an asset's records gives you the total, and you get it from Bitcoin rather than from us.

Getting from "roughly" to "exactly" took a second attempt. The first version of the record stored a fingerprint of the details rather than the details. A fingerprint only works backwards: you can confirm one you already know, but you cannot look at the blockchain and ask which records belong to a given asset. So the only number anyone could compute was the total across every asset and every stranger — a ceiling, not an answer. Writing the asset's name into the record in plain sight fixed it, and cost 32 bytes.

A checked model, and code that didn't match it

Between those two versions we shipped a bug that is worth describing, because the way it survived is the interesting part.

Before writing the rule we modelled it, using software that explores every possible sequence of events looking for a way to break a stated property. The model said: a coin counts only if its own creation is on the blockchain. Good rule. Then we wrote the code, and the code compared amounts.

Those sound alike and are not. An attacker waits for somebody honest to publish a creation of 1,000, invents their own asset that also creates 1,000, and hands out the paperwork. Every wallet's check asks "is there a confirmed creation of 1,000?" and the honest person's record answers yes. Free money, on round numbers that collide by accident.

No amount of model-checking would ever have found that, and it is worth being blunt about why: the model does not know what the code says. A verified model plus a sloppy translation of it is an unverified system, and the gap between them is invisible from either side. We found it by reading the two next to each other. The weak rule is now a module in the model of its own, so if anyone ever writes it again, the checks fail.

The tool that nearly shipped a hole

We have a script that measures how good our tests are by deleting one safety rule from the proof system at a time and checking that something fails. It puts the rule back afterwards.

A run got killed by a timeout partway through. It did not put the rule back — the cleanup only ran for one kind of interruption, and this was the other kind. So a safety rule sat commented out in the working files. Then the next run started by copying those files over its own backups, which destroyed the only good copy, and reported a result that looked completely ordinary: one measurement fewer, one problem fewer. Both numbers had moved in the direction that looks like progress.

This repository keeps exactly one commit, rewritten each time. There is no earlier version to recover. A routine "commit everything" would have published a proof system with a rule missing and erased the copy that had it.

Fixed in the order that matters: the tool now refuses to start if the files are already damaged — that is the check that survives even being killed outright — and it catches the interruptions it can, verifies its own cleanup, and says so out loud. The build now fails on the marker itself. The bad measurement stays in our records, labelled void, rather than being quietly replaced.

And a checklist item that had never run

Same day, same category. We keep a runbook that checks every property of every model — the slow, thorough version, run by hand because it takes hours. Running it in full after this work, it reported a failure in a model we had not touched.

The runbook was asking for a scenario that no longer exists. It had been renamed, the line naming the old one was never updated, and nothing complained, because the only thing that would have complained is the run we were doing for the first time in a while. A dead line is worse than a missing one: the file reads as though the case is covered.

One thing worked exactly as intended. The runbook treats a crash as a failure rather than a pass — we wrote that rule earlier for a different reason — so a scenario that could not be found came back red instead of being quietly skipped. Without it the line would have looked fine forever. The seconds-long check that runs on every change now verifies the names too, so the next one fails immediately rather than waiting for someone to spend an afternoon.

Deleting the channels — and what it bought

We had a design for instant payments between people who transact regularly: a channel, where two parties keep signing newer versions of a shared balance and only the latest one counts. It was specified in detail and it had the largest formal model in the project — twenty-seven of our fifty-nine machine-checked properties, more than the money path itself.

None of it was built. It had sat under the label "designed, modelled, not built" for months, and that label is how unwritten code gets counted as progress. We deleted the specification and the model.

The suite went from hours to five minutes. Channels was not merely the largest model, it was the slow one — a single deadlock check took forty-five minutes, and one depth further never finished at all. That is why our thorough verification run was a manual afternoon nobody did often. And because it could not be checked as deeply as everything else, it was also the only part of the suite running at a shallower bound: every remaining check now runs at the full depth, where before a third of them did not.

The thing we actually gained is not speed. A check that takes an afternoon runs when someone remembers; a check that takes five minutes can run on every single change, automatically, forever. We had been carrying a large body of careful work about software that does not exist, and paying for it by verifying the software that does exist less often. Deleting it made the remaining verification both faster and stronger, which is not a trade — it is what happens when you stop maintaining the wrong thing.

The reasoning is written down and the design is in version history. If we build instant settlement later it gets a fresh model, written against code, and a fresh review gate. Until then we would rather say plainly that we do not have it.

Retiring the BIP-110 page

We used to keep a page arguing, rule by rule, that Ultraviolet complies with BIP-110 — a proposal to tighten how much data a Bitcoin transaction may carry. The argument was good and we are not withdrawing it: our data is monetary, it is prunable, it never enters the set of unspent outputs that every node must keep forever, and one payment is a 64-byte push.

We have retired the page anyway, for a reason worth stating. It made a precision argument — this many bytes, this far under the limit — and precision arguments rot when the protocol moves. The new creation record is 76 bytes of data in a 79-byte script, against an 83-byte limit. Still compliant. But the page's headline was "we pass all of it, today", and keeping that true would mean re-deriving the arithmetic every time anything changes, on a page about somebody else's draft proposal that may never be adopted.

We would rather have one fewer page that could quietly become wrong. The byte budget now lives next to the code that produces it, where a test asserts the exact script size and the remaining margin — four bytes — and fails if either moves. That is a better home for a number than a webpage. We gave the argument a good shot; it is in this entry now.

2026-07-27

Two notes of one can finally pay two

A wallet holding two coins worth 1 each, owing 2, could not pay. At all. Not slowly, not awkwardly — the command refused. A payment spends exactly one coin, so if no single coin covers the amount, there was no payment to make.

It now sends two payments that add up. That sounds obvious, and the reason it took thought is that combining coins inside one payment is genuinely dangerous: a machine-checked model of this protocol shows two coins spent together can deadlock, with both consumed and nobody paid. Sending them as separate payments sidesteps that entirely, because each one either lands or does not, independently.

We did not want to close this on the strength of that paragraph. The model directory still contained a module proving the payment impossible, so we added one for what the wallet actually does — and checked it. The new one holds where the old one fails. The honest cost: each coin means another Bitcoin transaction and another fee, and a payment can now arrive partly, which is a new thing to reason about. Better than the alternative, where one interfering transaction consumes every coin at once.

A fix that wasn't running

Yesterday we wrote that small payments were safe at one confirmation because the wallet re-checks after the blockchain reorganises. Today we made that true.

The re-check was real, but it read from an index that never forgot anything, had no idea a reorganisation had happened, and reported a withdrawn payment as getting safer with age. The index now notices — with a single question to the node, because a block's identity commits to its entire history, so if the latest one still matches, nothing underneath it changed.

Then we pointed a real Bitcoin node at it, and it failed. The wallet detected the reorganisation and still kept a coin whose payment had vanished. The detection happens lazily, during a lookup — so checking "has anything changed?" before doing any lookup read yesterday's answer. The wallet was permanently one command behind the chain. That is not a bug any unit test we wrote would have found, because every unit test asks the question after something has already looked.

The test now covers both endings: a payment that gets re-included in the new chain, where the coin must survive — a wallet that panicked and quarantined a perfectly good coin would be its own kind of bug — and a payment lost for good, where the coin must be frozen. And we deliberately broke the fix again afterwards to watch the test fail, because a test nobody has seen fail is not evidence of anything.

Getting a real node to lose a transaction on purpose took three tries and taught us three things worth writing down: regenerating a block on a fork produces a byte-identical block that the node rejects as a duplicate; the saved memory pool is written on the shutdown before you disable it; and the node's own wallet helpfully rebroadcasts the very transaction you were trying to make disappear.

Looking for one bug's relatives

A forgery was found in this project's proof system earlier today. The interesting thing about it was not the hole itself but its shape: the rules were all correct, and the bug lived in something the rules quietly assumed and nothing checked. So we went looking for relatives, and found four.

The worst was the same bug one layer out. A proof is checked against a set of security parameters — how much redundancy, how many spot-checks. Those live in a configuration object, and every function that checks a proof simply accepted whichever configuration it was handed. Anyone building on this could have passed one with the security turned down to almost nothing, and every check would have passed happily. Nothing in our own code ever did that, which is exactly the problem — it was protected by good manners, and so was the trace height that got forged. The configuration is now wrapped in a type that only this library can create, so a weakened one is a compile error. We tested that by writing a program that tries it; it doesn't build.

One check evaporated in release builds. The number of public values a proof carries was verified only in debug mode, and a mismatch would have crashed rather than rejected. It's a real check now. That makes four separate obligations the verifying code carries outside the mathematics, and anyone reimplementing it has to reproduce all four.

And nothing tied a proof to this protocol at all. Fixed, though with a caveat we wrote down rather than glossed: it binds proofs to Ultraviolet, but the two different circuits are still told apart by their shape rather than by a label.

The pleasant surprise

A proof's table has leftover rows at the end, and an audit listed six kinds of cell there as unconstrained — free for a prover to fill with anything. We wrote a test to fill them with garbage and confirm it couldn't matter.

The test failed, and the reason was good news: five of the six are not free after all. Only one genuinely is. The leftover rows are considerably more locked down than anyone believed. The test now asserts what is actually true, and comes with a companion that deliberately breaks something to prove the test can still detect a problem — because a test that cannot fail tells you nothing, which we learned the hard way earlier today.

Two live bugs, found by asking what the list got wrong

Junk mail was immortal. When a payment was rejected, its file was left sitting in the inbox — so every future check re-examined it, forever. One piece of junk from a stranger cost real work on every scan for the rest of time. Now rejections are sorted: a payment that simply hasn't settled yet is kept, and one that can never become valid is thrown away. There is also, at last, a limit on how long a payment's history can be, so a stranger can't hand you an arbitrarily large amount of work.

And a safety fix turned out not to be running. Our own notes said small payments were safe at one confirmation because the wallet re-checks after the blockchain reorganises. It does — against a test double. Against the real Bitcoin backend the re-check reads an index that never forgets anything, has no idea a reorganisation happened, and reports a withdrawn payment as getting safer with age. So the mitigation we were relying on did not exist where it mattered. Small payments now wait for three confirmations, which is the other repair the mathematics proved and the one that actually works. It costs a few minutes on small payments. The proper fix is written up as open work rather than assumed done.

Also: a review of how data is encoded, which we owed. The verdict is that nothing dangerous depends on it, and the reason is worth stating because someone could easily break it later — everything that matters is hashed from numbers, never from encoded bytes. A future feature that hashes an encoded record instead would silently make a whole class of problem live. That is now written down as an invariant rather than left as a happy accident.

2026-07-27

We nearly published numbers for software we'd already replaced

This morning we measured how long a payment takes to prove, put the figures on this site and in four specification files, and moved on. Then, hours later, we fixed a privacy bug by replacing the random-number generator at the heart of the proving code with a proper cryptographic one — and did not re-measure. For most of a day, every performance number we published described software that no longer existed.

It was not a small part of the code to change. Making a payment private involves generating something like half a million random numbers, and we swapped the fast, insecure generator for a slower, secure one. There was every reason to expect that to cost something.

Re-measured on the phone: it cost nothing detectable. A private payment takes 0.28–0.31 seconds on an iPhone 17 Pro Max, against the 0.26–0.31 published. The non-private variant, which does not use that generator at all, drifted by exactly the same small amount — which is the tell that the difference is a warm phone and a busy laptop, not the change. Security was free here because the expensive part of proving is arithmetic and hashing, not generating random numbers.

And then we tried it on a cheap phone

"A flagship can do it" is a weaker claim than it sounds, so we borrowed the other end of the range: an iPhone 16e, the cheapest iPhone Apple currently sells. A private payment takes 0.35 seconds there, against 0.31 on the flagship — about a sixth slower, across a gap of several hundred pounds.

The memory result is the more interesting one, and it nearly fooled us. The cheap phone appears to need 25 MB more. It does not: the prover's own share is 261 MB against the flagship's 259 MB, a difference of two. The entire gap is how much memory iOS and the app shell were already using before any proving started — 43 MB on one, 19 MB on the other. Had we quoted the headline figure alone, we would have published a hardware difference that does not exist.

The numbers survived. The process did not deserve to get away with it, so we have added a check that runs on every build: proof sizes are pinned to the byte, and the cost of a private payment relative to a plain one is bounded. That second one is deliberately a ratio rather than a stopwatch reading — a ratio cancels out how fast the machine happens to be, so it can be strict without failing at random. We tested that the check actually fails when fed a regression, because a guard nobody has seen fail is not a guard.

And the repository was 99.6% junk

A fair question arrived while this was going on: why does every commit touch millions of lines? Because it did. The demo script writes its output — wallets, payments, proofs — into a folder that was never added to the ignore list, so every run committed all of it. The tracked project was 3,649,694 lines, of which about 3.6 million were generated files nobody reads.

The reason it was so enormous turned out to be a real bug rather than mere clutter. Wallets were being written as indented, human-readable text — and a wallet contains the full proof history of every coin it holds. Each individual number in each proof got its own line. One demo wallet was 46 megabytes across 2.77 million lines. That is not just a repository problem: real wallets used the same code, so anyone's wallet would have bloated the same way, on a phone, where it matters most. Storing it as binary instead took that wallet from 46 MB to 2.6 MB — eighteen times smaller — and encrypted wallets were paying the same cost, because the bloated version was what got encrypted.

The project is now 20,385 tracked lines and a fresh download is 1.5 MB. This is the second bug of exactly this shape found today; the first was payments being stored as hexadecimal inside text, which doubled them. Both were invisible because both were merely wasteful rather than wrong.

A payment rode Signal

A real Ultraviolet payment — proved, settled, and worth something — travelled between two wallets over a genuine Signal Protocol session, and the receiving wallet accepted it.

"Genuine" is the load-bearing word. This uses Signal's own code, taken from Signal's repository at a release tag. There is a package on the Rust package index with a Signal-sounding name that is not Signal's; using it while saying "real Signal" would have been false, so we checked. The handshake is the real one, including its post-quantum step, and so is the ratchet that follows.

The payment is wrapped twice, by different cryptography, for different reasons. Our own envelope makes it unreadable to whoever carries it, and would be there if it travelled by post. Signal's layer makes it look like every other Signal message. Neither is redundant: drop ours and the person running the server is someone you have to trust; drop Signal's and the world can see who is talking to whom. The money never inherits its privacy from the messenger.

The test runs a deliberately stupid relay in place of a server, and then interrogates it. It saw 216,147 bytes addressed to a phone number. The bytes do not compress, which is what ciphertext looks like, and contain no trace of the payment inside them. That is the claim worth having: a carrier routes something it cannot read and cannot identify as money.

What we could not do, and why we are saying so

We have not run this on Signal's actual network, and cannot: Signal blocks third-party clients. The honest version has always been "run your own server", so we tried to.

Signal's server software builds — we compiled all of it. Running it is another matter. There is exactly one documented way to start it, tucked inside a test class, and it comes with its own warning that most features won't work. We got it as far as starting the databases it needs before it gave up on a networking detail.

We stopped there on purpose rather than pushing through, because the mode that starts is the mode with all the interesting parts switched off. A real one needs a database most people have never installed, several clusters, and credentials from Apple, Google, a payments processor, an app store, and — the one that really stops you — a separate service for sending verification texts, which has no public implementation. Signal says plainly that they cannot help you run it elsewhere. They are not being unhelpful; it is simply not built to be self-hosted.

So one claim in our spec is still only an argument: that carrying payments needs no change to a Signal server at all. We believe it, the design gives it a hard technical floor, and we have not demonstrated it. It is filed as open rather than quietly rounded up to done.

Also shipped today: the sealed payment on disk was being stored as hexadecimal inside JSON, which doubled every byte for no benefit. It is raw bytes now — 428,923 bytes became 214,460 for the same payment. That matters more than it sounds, because a coin's proof grows with its history, and this is the thing a phone has to upload.

2026-07-27

We asked four strangers to break the circuit. One of them did.

The forgery was total. It cost about twenty milliseconds, required no key, no seed and no secret of any kind, and it let an attacker create money that never existed. It is fixed, it is covered by two tests that will fail loudly if it ever comes back, and no Ultraviolet has ever held real value — signet coins are play money and that is the entire point of testing there. But it was real, and this is the entry that says so.

What was wrong

A proof of a payment is a table of numbers. Ours is 1,024 rows tall, and the rules that check a payment are written as arithmetic over that table. Some of those rules only wake up near the bottom of it — the row where the signature check finishes is what switches on everything that examines the money: does the coin exist, does its spend-marker follow from it, do the amounts add up, does the spender hold the key.

The proof got to declare its own height, and nobody checked it. Hand in a table eight rows tall and the wake-up row never arrives. Every rule about the money stays asleep. The proof is still a perfectly valid proof — of nothing whatsoever. Meanwhile the receiving wallet carefully works out what the payment claims and hands those numbers to a checker that no longer reads them.

One reviewer built exactly that: eight rows of zeros, a coin they did not own, an invented spend-marker, and an output paying themselves more than the asset's entire issuance. Another independently walked it all the way up the stack — publishing the record to a chain, waiting for it to confirm, and handing the result to the receiving wallet, which said yes.

Why our own tests could never have caught it

Every test we had generates an honest payment and checks it is accepted, or breaks one thing and checks it is rejected. Both only ever explore payments we thought of. This bug was not a mistake inside a rule — the rules are fine. It was a mistake in something the rules quietly leaned on, which no rule stated and no line of code enforced. Our audit brief had literally written down "1,024 rows" as a fact about the system. It was an assumption wearing a fact's clothing.

The fix is three lines: the height a proof declares is now part of what it must prove, and anything else is refused before the proof is even examined. That makes three separate obligations the checking code carries outside the arithmetic — and this third one is the easiest to lose, because nothing inside the proof hints that it exists.

The fix had its own bug, and that is the real lesson

The first version rejected the forgery correctly. It also rejected every honest private payment, because a privacy-preserving proof legitimately uses a slightly taller table than a plain one, and the check compared against the plain number. It passed 43 of 44 tests and looked completely fine. One of the reviewers read it and spotted the off-by-one within the hour.

That is the argument for outside review in miniature — and we would rather show it than claim it. Both the break and the fix's own bug were found by adversarial reading. Neither was found by us, and neither would have been.

The other thing they found: our private proofs were not private

Separately, the proofs that hide payment amounts were hiding them behind a mask generated from a fixed number written in the source code — a number anyone reading our public repository could copy. Proving the same payment twice produced byte-identical proofs, which is a fingerprint of the payment and the opposite of what a zero-knowledge proof is for. The mask now comes fresh from the operating system every time, from a generator built for cryptography rather than for speed. This never put money at risk — amounts were the thing exposed, not funds — but the site claimed amount confidentiality and the claim was not true.

What survived

Worth stating, because a page about two breaks reads worse than the situation is. The reviewers also tried, and failed, to: create money by making the amounts not add up (eight separate attempts, including the specific arithmetic trick the defence was built for); reuse a proof for a different payment; forge a spend-marker; spend a coin they had already paid to someone else; and swap one asset for another. Each of those died for a reason someone traced and wrote down. The copied hash function at the core matches its original exactly, and a setting we got wrong once is now impossible to get wrong silently. Those are now checked rather than believed, which is a different thing from before.

The full brief we hand a reviewer is AUDIT-BRIEF.md, now corrected, and carrying a new instruction: find another load-bearing assumption nobody enforces, because we no longer assume this was the only one.

2026-07-27

The phone proves its own payments

A payment proof now takes about 0.28 seconds on an iPhone 17 Pro Max. Not in a simulator on a Mac — on the phone, in a signed app, from a plugged-in handset.

This closes the last open question about whether Ultraviolet can be a real wallet. Making a private payment means producing a proof, and producing a proof needs the payment's secrets: which coin you are spending, how much, and the key that controls it. If a phone were too slow, the only way to send would be to ship those secrets to a server and ask it to prove on your behalf — which hands a stranger exactly the information the whole design exists to hide. A quarter of a second means nobody ever has to. The secrets stay on the phone.

For scale, the virtual machine this replaced needed two minutes and 9.7 GB for the same payment. That is where "a phone could never prove this" came from, and it is no longer true of anything in this repository.

Two of our own memory numbers were wrong, in opposite directions. Peak memory is measured per process, so proving both configurations in one run reports the two of them added together — a figure that belongs to neither. Separating them moved the desktop number from a meaningless 146 MB to 117 MB. In the other direction, an iPhone app costs 20–25 MB just to exist before any proving starts, and counting that against the prover overstates it. Both harnesses now run one configuration per process and report the app's baseline separately.

And one gap we could not explain. The private configuration wants around 279 MB on the phone against 117 MB on the Mac, while the non-private one matches closely, 56 MB against 67 MB. So it is something about that one configuration, not about phones. The obvious suspect was parallelism, and it is not: the phone uses six threads to the Mac's ten — fewer threads, more memory — and forcing both to a single thread changed neither the memory nor the time. Our best guess is that the two systems differ in how eagerly they hand freed memory back, and the private configuration churns through a lot of large short-lived buffers. That is a guess. We are recording it as one, because 279 MB is comfortably within budget either way and a wrong explanation would be worse than an admitted gap.

The app that produces these numbers is in the repository at ios/UVProbe, so the measurement can be repeated rather than taken on trust.

Real money on signet, and a hole in our own spec

Two of these are milestones. One is a design error we had been carrying in writing for weeks, and the way it surfaced is the more useful story.

The spend anchorA coin now commits to t = H(key) rather than to the key itself, and the circuit makes a spender prove it knows the key behind t. One extra row, nine columns, no change in trace height — the section had spare rows.

AddressesAn address is a batch of one-time slots plus a scan key, handed over once. After that a payer can pay whenever it likes with the payee offline, and no payment needs an invoice.
It builds for iOSThe whole payment stack compiles for iOS and runs correctly in the simulator, with proof sizes byte-identical to the Mac build. The simulator uses the Mac's own chip, so this established the port and not the speed. The speed came later the same day, on an actual phone — see the entry above.
Sealed paymentsPayments travel encrypted under hybrid ML-KEM-768 + X25519 — an attacker has to break both. The receiver finds its own mail by trying to open each envelope, because a "this one is for you" marker is exactly the metadata worth hiding. A test proves both halves matter: swap either one's ciphertext and the key breaks.

The spec was wrong, and it said so out loud. Our own written design said the sender should derive the coin's one-time key from a shared secret. Work through it and the construction refutes itself. The sender chooses that shared secret. So the sender could spend the coin it had just paid out.

The deeper reason is not a slip of wording. Elliptic curves let you tweak a public key in the open while only the owner can tweak the matching secret, which is what stealth addresses are built on. A hash-based key is a hash tree over its own secret, and there is no public operation that produces one whose secret only someone else knows. Getting that from hashes alone would be key agreement from a hash function, which is not available. So the property had to come from somewhere other than the key derivation — hence the anchor, and hence addresses that hand over a batch of slots.

The same change closed a privacy leak that was live until now. When a coin committed to the key itself, the payer necessarily learned it — and the spend marker is a fixed function of that key. Every payer kept a permanent watch on the exact moment its payment was spent onward. It now holds the anchor and can compute nothing. One more honest note: removing the first handover entirely would need a single long-lived secret in every spend, which would make the proof's privacy property load-bearing for fund safety too. Not taken, and gated on the review below.

2026-07-26 · the measured case

Why the virtual machine had to go

These are the numbers that justified deleting a year of work. They are kept here rather than on the benchmarks page, which prices what a payment costs today; this is the archaeology of a system that no longer exists. Re-running any of it means checking out a commit from before the rewrite.

Memory was the harder wall, because it could not be tuned. Smaller shards made the proof bigger and did not reduce memory: the memory is the execution trace, the row-by-row record of every step the program took. A three-input spend is ~12M cycles and died outright on a 16 GB machine — SP1 logged Memory usage is high: 80.06% and the process was killed. The only lever on RAM was a smaller circuit, which is the same lever as speed.

And 77% of the work was checking one signature. Of 5.18M cycles per hop, SLH-DSA verification over SHA-256 was 4.0M, in-circuit recursion 1.15M, and the actual transfer logic 88,724 — under 2%. Recursion is the part everyone assumes is ruinous; measured by comparing a chained hop against a first hop, it cost +17.3 s of 124 s. Nearly all of the signature's cost was machinery for making a key reusable, and Ultraviolet does not need reusable spending keys: a coin is spent exactly once and the protocol already enforces that. That is what pointed at WOTS+.

The hash swap was worth less than it looks, and that was the decisive finding. Called inside a proof, SHA-256 with SP1's accelerator cost 1,353 cycles against Poseidon2's 402 — 3.4×, not the 100× one might guess, because SHA-256 was never running unassisted. Projecting the full stack of improvements: one-time signature over SHA-256 ~39 s, over Poseidon2 ~26 s, and a hypothetical hop with no signature at all ~21 s. Those projections are a fit, not a measurement. Read the last one as a floor: after switching both hash and signature you land within a few seconds of the cost of doing no signature work whatsoever. Everything left was the cost of the virtual machine itself, which is what made the rewrite the right move rather than more tuning.

An awkward discovery, from reading SP1's source rather than its marketing. The proofs Ultraviolet shipped on the zkVM were never zero-knowledge. Underneath, SP1 is a STARK, and that raw STARK does no blinding in the machinery that commits to the trace, so the proofs carried genuine fragments of the sender's private data. SP1's zero-knowledge came from a final wrapper step Ultraviolet refuses on quantum-safety grounds — refusing the wrapper refused its privacy too, and nobody re-checked. The chain never saw amounts or parties either way; what leaked was toward the person you pay. The replacement circuit's hiding configuration genuinely is zero-knowledge, so the rewrite was not a speed project with a privacy side effect. It is both.

retrospective · the whole build so far

Six things we believed that measurement disproved

A page of clean numbers proves nothing about how carefully they were gathered, which is why these are written down. Two of them would have sent the project down an expensive road.

"Proving takes ~45 minutes per payment"off by ~27×

Never measured. It was an extrapolation: take a small circuit's timing and multiply by the cycle increase. It sat in the spec directly beside genuinely measured numbers, with nothing marking it as a guess. Proving does not scale linearly with circuit size. The real figure is about two minutes. The project's own demo scripts had been quietly running at that speed the whole time.

Caught by: finally running the benchmark.

"Receiving is O(1) — one proof, any history"retracted twice, in two halves

First half: even when the recursive proof was constant-size, a recipient still had to confirm that every past hand-off settled on Bitcoin. That is one chain lookup per previous owner. A formal model found the gap the hard way. Skipping those checks let an attacker make two honest wallets accept the same coin, doubling the money supply. So O(1) was only ever true of validity, never of safe receiving.

Second half: the constant-size proof itself went with the zkVM. Recursion over a hand-written circuit is a large piece of new consensus-critical work. So today one fixed-size proof ships per hop, and the receive bundle grows with a coin's history. The accumulator design (spec/99) is what would make receiving O(1) for real, proof and lookups both. It is future work, stated as such.

Caught by: writing a machine-checked model of the protocol.

"Verification is milliseconds"given data we don't have

True given an indexed view of the chain. A phone has neither the index nor the ability to build one, so it has to ask a server. Asking a server reintroduces a privacy leak and a trust assumption that the claim implied were absent. The same blind spot twice: the cryptography got carefully priced and the data access did not.

Caught by: reading our own lookup code, which re-scanned the entire chain on every single query.

A 10 ms verification requirement, invented and then withdrawnnear-miss

Four pass/fail thresholds were set before testing the hand-written circuit. Three were derived from real constraints. The fourth was verification under 10 milliseconds, a round number with no reasoning behind it. The circuit came in at 10.7 ms and "failed". Under the stated plan, that meant abandoning the approach and switching proof systems.

Only the recipient ever verifies, once, per payment received. Ten milliseconds is invisible. The gate was standing in for a different concern, which was written down properly afterwards: without recursion, verification and bundle size grow with a coin's history.

Caught by: being asked "wait, why is 10 ms a requirement?"

Benchmarking the wrong hash as a "safe upper bound"false negative

The first feasibility test used Keccak instead of Poseidon2. The reasoning: Keccak is more expensive per hash, so passing with it would be conservative. That is true per hash and irrelevant overall. The Keccak circuit is 2,633 columns and 24 rows per hash, against Poseidon2's 313 columns and one row. That is roughly 120× more work for the same number of hashes. It failed three thresholds, and the failure meant nothing.

Caught by: the trace dimensions being absurd on inspection.

Projecting proof size against the wrong variablesame test, second error

Cost was measured against circuit height, then extrapolated to predict proof size. But sweeping height across a 64× range moved proof size barely at all: 711 → 855 KB. Proof size and verification scale with circuit width, so the whole projection was measuring nothing. Fixed by testing width directly. Width also happens to be the parameter you actually control when designing a circuit.

Caught by: the numbers being suspiciously flat.

The pattern worth naming: every one of these survived until something outside our own reasoning was pointed at it. That something was a measurement, a model checker, or a blunt question. Cryptographic cost is the part that feels rigorous, so it gets measured. The data access, the trace width, and the requirements get assumed. Assume nothing that a benchmark, a formal model, or a "wait, why?" can check for you.

2026-07-26 · the rewrite

Throwing away the prover

The project spent most of its life on a general-purpose zero-knowledge virtual machine, a zkVM. It let the protocol be written once in Rust and run identically on a laptop and inside a proof. That is a genuinely good trade, and it is how the design got as far as it did. Then we measured it: 124 seconds and 9.67 GB per payment. Verifying one signature accounted for 77% of that, and the memory could not be tuned down. A phone could never do it.

Replacing it meant hand-writing the circuit. It also meant owning the circuit's soundness, which a zkVM gives you for free. Two obstacles we had budgeted for dissolved instead. The signature chains needed no lookup arguments, because a boolean selector gates each step. And binding the signature to a message needed no in-circuit decomposition: the verifier supplies the digits, so there is no prover-chosen value anywhere. One latent bug surfaced on the way. A boundary flag was boolean but positionally free. That was harmless while the proof bound nothing, and fatal the moment boundaries indexed public values.

Also deleted this week: recursion. Verifying the previous proof inside each new one made receiving constant-size, however long the history. Re-implementing that over a hand-written circuit is a large piece of new consensus-critical work. So the design now ships one small proof per hop, and the receiver checks each one. That is an honest downgrade from O(1) to O(k), recorded as such rather than quietly dropped. An accumulator, not recursion, is what would restore it.

2026-07-25 to 07-26 · what the models found

Two bugs no amount of testing would have found

FoundThe defect
Supply inflationEvery wallet ran the double-spend check correctly, and one coin still became two. Checking first-occurrence at your own hop does not compose. An attacker routes the losing branch of a double-spend through a second wallet of their own, and that wallet simply skips the check. Nobody can see this happen, because nothing lets you verify that someone else ran a check. Both honest receivers then pass their own checks and accept. The fix: validate the coin's whole lineage — every hop in its history — not just your own. The eight-step counterexample is replayed as a test.
The one-time key trapThe new signature scheme reveals its private key if one key ever signs two different messages. The obvious guard is to remember that you signed and refuse when unsure. That guard is safe, and it freezes live money: a record that loses its race leaves the coin unspent on-chain and the key unusable. The only discipline that is both safe and live is to record what was signed and replay those exact bytes. That is now the rule. It is why the double-spend attempt on signet produced no transaction at all.

A model is only as honest as its choice of what the adversary controls. The first model found a real bug and was blind to a second one of equal severity. It missed it purely because it handed the system the very thing under test. Eight modelling and tooling traps produced confident-looking wrong answers along the way. They are recorded in the repository rather than quietly fixed.

2026-07-25 · direction

Two decisions that changed the shape

The carrier became Signal. Payments travel as ordinary encrypted messages with the proof as an attachment, and the messenger cannot tell money from a photo. The honest cost went into the spec at the same time: Signal blocks third-party clients, so a demo needs a self-hosted server. The old claim of "nothing to deploy" is dead. What survives is that carrying payments needs no server changes. Durable storage also became a separate role, because Signal delivers and then deletes.

An audit found four consensus-critical gaps. Spend authorization lived outside the proof. The spend marker was not bound to ownership. An asset id was not bound to its issuer. And duplicate inputs could inflate the supply. All four are addressed in the current design. A formal model then found a fifth that was worse than any of them.

What is not done

Nobody outside this project has reviewed the proof circuits. That is the single largest risk, and it grew when the zkVM was deleted. A general-purpose prover's soundness is one artifact that many people review. A hand-written circuit's soundness is every column being constrained. A test suite built from honest inputs cannot find a column nobody constrained.

Also open: the Signal client, channels, and spending several coins at once. The open problems list is authoritative — if it is not there, it is not open.
