1 · The circuit

What one payment costs

This is the finished money-path circuit, actually proving and verifying. One complete hop fits in a single table of 16 rows × 361 columns. A commitment here is a hash that pins down a coin's amount without revealing it. The hop opens the input commitment, derives the nullifier (the spend marker), opens the two output commitments, checks conservation over range-checked 16-bit limbs, and proves the spender knows the preimage of the coin's spend anchor — the authorization, standing alone, with no signature:

ConfigurationTraceProveProofVerifyPeak memory
Standard16 × 361~0.011 s81.5 KB~1.1 ms4 MB
Hiding (the payment format)16 × 361~0.01–0.02 s117.2 KB~1.6 ms5 MB

At 16 rows the prover is dominated by fixed FRI overhead, so prove time is a range across runs, not one sample; trace, proof size and peak are deterministic. Reproduce with UV_MEASURE=standard|hiding cargo run --release -p uv-air --bin measure.

This circuit is a decision, not a teaser. Spend authorization is in-circuit knowledge of the note's committed anchor preimage, Fiat–Shamir-bound to the exact transfer — 16 rows, one Poseidon2 permutation each. It replaced an in-circuit signature on 2026-07-29 under a rule recorded before measuring, which the signature then missed by 6.7×; the table collapsed from 1,024 rows to 16, an order of magnitude faster on ~23× less memory.

Speed was never the stronger reason. Proving twice reveals nothing, where signing twice under one key had disclosed it — so losing wallet state no longer risks a secret. The honest cost, stated because it is real: zero-knowledge stops being privacy-only and becomes load-bearing for funds, since the witness now is the authorization. That is contained by one-time anchors. Rule, numbers and the full record: spec/99 [PROOF-AUTH].

On an actual iPhone

Everything above is a Mac. The number that decides whether this can be a self-custodial wallet is the phone's, because making a private payment means proving one, and proving one needs the payment's secrets. A phone too slow to prove would have to send those secrets to a server — which hands a stranger exactly what the design exists to hide.

Measured 29 July 2026 in a signed Release build on an iPhone 16e (A18), iOS 26.2.1 — deliberately the cheapest iPhone Apple sells, because "a flagship can do it" is the weaker claim. Six threads:

ConfigurationProveProofVerifyProver's share of memory
Hiding (the payment format)0.006–0.012 s117.2 KB1.25–1.35 ms1 MB
Standard0.007–0.008 s81.5 KB0.89–1.08 ms2 MB

Read the third column first: proof sizes are byte-identical to the Mac's. Same circuit, same parameters, so a faithful port is checkable from the bytes rather than taken on trust. And the phone is not the bottleneck anyone expected — a private payment proves in about a hundredth of a second on a mid-range phone, using about a megabyte more than the app already occupied.

For scale, and because this page withdrew a number earlier the same day: the signature circuit these replace took 0.331–0.354 s and ~260 MB of prover memory on this same 16e. Those figures were honest measurements of code that no longer exists, so they were removed rather than quietly reused — and the replacement is roughly 30× faster on a fraction of the memory. The witness never leaves the device in either case. Reproduce with the app's own Status → Run diagnostics, which writes a transcript.

A gap that outside review still owns. The tests show the circuit agrees with a reference implementation on the cases tried, and the mutation sweep shows which constraints a test would notice the loss of — and the latest sweep isolates 16 of 16. Nine of those were survivors until 2026-07-30, resting on the fact that they were byte-identical to constraints of a deleted circuit that had swept clean. That is an inheritance argument, not a test, and it is retired: a probe that evaluates the constraint system without proving, recording each check separately, closed all nine. The same probe answers a question a deletion sweep structurally cannot ask — all 361 of the circuit's 361 columns provoke an objection when perturbed, so no column is a value a prover may choose freely. None of that is the same as proving no other input could satisfy the circuit. That gap needs professional review, and it is the kind of bug that mints money if missed.

Why these proof parameters

Proof size and verification cost scale with the number of spot-checks the verifier makes, and security depends on the product of those checks and a redundancy factor. So you can raise redundancy, cut checks, hold security constant, and get a smaller proof — paying in prove time, which had enormous headroom. The sweep below fixes a Poseidon2 hashing load and varies only the FRI redundancy, to isolate the size/time tradeoff from the money-path trace; the chosen row is the configuration the payment format uses:

RedundancySpot checksSecurityProveProofVerify
2×100~100 bits0.010 s406.9 KB3.20 ms
4×50~100 bits0.032 s227.4 KB1.79 ms
8×34~102 bits0.048 s170.7 KB1.33 ms
16× (chosen)25~100 bits0.040 s137.7 KB1.04 ms

Hence blowup 16 with 25 queries, for roughly 100-bit soundness. Those parameters are a deliberate choice and a fair thing for a reviewer to challenge.

2 · Privacy, priced

What hiding costs

A zero-knowledge proof reveals nothing beyond the fact that it checks out. The hiding configuration is genuinely that; the standard one is not, and exists for benchmarking and for proofs over public data. Hiding costs about 1.4× the proof size of the standard configuration and, at 16 rows, a prove time within run-to-run noise of it — the blinding mask is a small addition to so short a table.

That price bought a decision: hiding is the payment format, and the only one. A note carries one hiding proof per hop, so amounts, keys and randomness stay confidential along a coin's entire lineage, from issuance to whoever holds it now. A plain-witness mode was considered and rejected — two validation paths is two consensus surfaces, and a mixed lineage inherits its weakest hop's privacy.

Numbers quoted in the journal for designs that were measured and then deleted are not reproducible from this tree — the code that produced them is gone, which is the point of having deleted it. They are recorded there with the dates they were taken.

Measure one configuration per process. Peak memory is a process high-water mark, so proving standard and hiding in the same run reports their union, which is neither one's cost — that mistake put a meaningless 146 MB on this page for a while. The harness now refuses to mix them unless you ask for both.

Hardware: one laptop, 16 GB RAM, CPU only, with other applications running, and an iPhone 17 Pro Max for the device row. No GPU, no proving service.
