1 · The circuit

What one payment costs

This is the finished circuit, actually proving and verifying. One complete money-path hop fits in a single table of 1,024 rows × 457 columns. A commitment here is a hash that pins down a coin's amount and owner without revealing either. The hop opens the input commitment, derives the nullifier (the spend marker), opens the two output commitments, checks conservation over range-checked 16-bit limbs, proves the spender knows the key behind the coin's spend anchor, and verifies the WOTS+ signature:

ConfigurationTraceProveProofVerifyPeak memory
Standard1,024 × 4570.070–0.084 s158.3 KB1.4 ms67 MB
Hiding (zero-knowledge)1,024 × 4570.202–0.241 s208.0 KB1.6 ms117 MB

The one-time signature check on its own, message binding and all, is 0.083 s / 150.0 KB on a 1,024 × 392 trace. The full hop is faster than the signature alone despite being wider, reproducibly. We have no explanation for that and are not inventing one; the plausible candidate is column chunking in the parallel transform.

The same circuit, on an actual iPhone

Everything above is a Mac. The number that decides whether this can be a self-custodial wallet is the phone's, because making a private payment means proving one, and proving one needs the payment's secrets. A phone too slow to prove would have to send those secrets to a server — which hands a stranger exactly what the design exists to hide. Measured in a signed app on two devices, chosen to be far apart in price: an iPhone 17 Pro Max (A19 Pro), iOS 26.5.2 and an iPhone 16e (A18), iOS 26.2.1.

Hiding (the payment format)16e (A18)0.331–0.354 s208.0 KB1.8–2.0 ms304 MB261 MB

Standard16e (A18)0.121–0.128 s158.3 KB1.5–1.8 ms81 MB39 MB

Both phones, deliberately. The 16e is the cheapest iPhone Apple currently sells and it is only ~1.15× slower on the payment format. The claim is that a phone can prove, not that a flagship can, and a two-tier price gap moves it by a sixth.

Read the memory columns together. The 16e's peak looks 25 MB higher, but the prover's share is within 2 MB of the flagship's — 261 MB against 259 MB. The whole difference is the host app's baseline (43 MB against 19 MB), which is iOS and UIKit rather than us. Quoting peak alone would have invented a gap that is not there.

Proof sizes are byte-identical to the Mac build, which is the useful signal: the port is faithful, not approximately faithful. About a third of a second and 279 MB is an ordinary thing for a foreground app to do, so the witness never has to leave the phone. The app that produces these numbers is in the repository at ios/UVProbe.

Two of our own memory numbers were wrong, in opposite directions, and both are worth naming. Peak memory is measured per process, so proving both configurations in one run reports the two added together — a figure belonging to neither. Isolating them moved the Mac figure from a meaningless 146 MB to 117 MB for hiding alone. In the other direction, an iPhone app costs 20–25 MB to exist before any proving begins, and charging that to the prover overstates it. Both harnesses now run one configuration per process and report the host's baseline separately.

An unexplained gap, stated as one. Hiding wants ~279 MB on the phone against ~117 MB on the Mac, while standard matches closely (56 MB vs 67 MB) — so it is specific to that configuration, not a platform-wide offset. Parallelism is ruled out: the phone reports six threads to the Mac's ten, fewer threads and more memory, and pinning both to a single thread moved neither the memory nor the time. The leading hypothesis is that the two systems differ in how eagerly they return freed pages, and the hiding path churns many large short-lived buffers. That is a hypothesis. It does not threaten the conclusion, since 279 MB is well inside budget either way, but quote the phone's number for a phone.

A measurement trap worth naming, since we fell into it. The first proof in a process pays for allocator growth and cold caches. Timing it therefore flatters whichever circuit runs second. Before the harness warmed up and isolated the two, the wider transfer circuit read as faster than the narrower signature circuit. That is impossible for more columns and more constraints. Warmed and isolated, the transfer circuit is still the faster of the two (0.067 s vs 0.083 s), reproducibly. We have no explanation for that and are not inventing one. The plausible candidate is column chunking in the parallel DFT.

Honest gap, closed. An earlier version of this circuit did not bind the signature to a specific message. It proved "some chain walk happened" and bound nothing. It now binds both message and key, pinned through 603 public values plus a constraint-pinned one-hot register. Public values are the handful of numbers a proof hands its verifier in the clear. The negative-test suite includes a forgery that satisfies the host-side key check and is rejected by the circuit alone. Still true: the tests show the circuit agrees with the reference implementation on the cases tried. That is not the same as proving no other input could satisfy it. That gap needs outside review, and it is the kind of bug that mints money if missed.

Why these proof parameters

Proof size and verification cost scale with the number of spot-checks the verifier makes, and security depends on the product of those checks and a redundancy factor. So you can raise redundancy, cut checks, hold security constant, and get a smaller proof — paying in prove time, which had enormous headroom. Swept on a bare 313 × 1,024 Poseidon2 circuit, one one-time signature's worth of hashing:

RedundancySpot checksSecurityProveProofVerify
2×100~100 bits0.010 s406.9 KB3.20 ms
4×50~100 bits0.032 s227.4 KB1.79 ms
8×34~102 bits0.048 s170.7 KB1.33 ms
16× (chosen)25~100 bits0.040 s137.7 KB1.04 ms

Hence blowup 16 with 25 queries, for roughly 100-bit soundness. Those parameters are a deliberate choice and a fair thing for a reviewer to challenge.

2 · Privacy, priced

What hiding costs

A zero-knowledge proof reveals nothing beyond the fact that it checks out. The hiding configuration is genuinely that; the standard one is not, and exists for benchmarking and for proofs over public data. Hiding costs 2.8× prove time and 1.3× proof size on the full hop — on the signature circuit alone, which has less to blind, 2.1×.

That price bought a decision: hiding is the payment format, and the only one. A note carries one hiding proof per hop, so amounts, keys and randomness stay confidential along a coin's entire lineage, from issuance to whoever holds it now. A plain-witness mode was considered and rejected — two validation paths is two consensus surfaces, and a mixed lineage inherits its weakest hop's privacy.

3 · Check it yourself

Reproduce every number

Everything on this page is committed and needs only a Rust toolchain — plus Xcode and an iPhone for the device row. The zkVM benchmarks referenced in the journal were deleted along with the zkVM; re-running those means checking out a commit from before the rewrite.

CommandWhat it measuresRuntime
UV_MEASURE=transfer-hiding cargo run --release -p uv-air --bin measurethe full transfer hop, hiding configuration, with its own peak memory~2 s
UV_MEASURE=transfer-standard … / UV_MEASURE=signature …the standard configuration; the signature circuit alone~2 s
ios/UVProbe (see demo/ios.md)the same circuits on a physical iPhone~1 min
./demo/local2.shend to end: issuance → two-hop payment → a payment split across two notes → double-spend attempt → reorg reconciliation. Six self-checks, all asserting rather than printingruns in CI
./demo/regtest.sha real bitcoind, two forced reorgs: one where the payment is re-mined and the coin must survive, one where it is lost and the coin must freeze~1 min, needs bitcoind
cargo test --workspace161 tests including real proofs and the negative-test suite~2 min

Measure one configuration per process. Peak memory is a process high-water mark, so proving standard and hiding in the same run reports their union, which is neither one's cost — that mistake put a meaningless 146 MB on this page for a while. The harness now refuses to mix them unless you ask for both.

Hardware: one laptop, 16 GB RAM, CPU only, with other applications running, and an iPhone 17 Pro Max for the device row. No GPU, no proving service.
