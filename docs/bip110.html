Ultraviolet & BIP-110

If Bitcoin clamps down on chain data, we're already the clean case.

The short version

We pass all of it, today

BIP-110 is a proposed one-year Bitcoin soft fork that restricts non-financial data in transactions. It is aimed at inscription and Ordinals bloat. It caps most new outputs at 34 bytes, OP_RETURN at 83 bytes, and data pushes at 256 bytes. (OP_RETURN is Bitcoin's data-only output, the one place a transaction can carry a small payload.) Ultraviolet complies with every one of its rules right now, with room to spare. Our on-chain data is minimal, monetary, and prunable, meaning a node can discard it once the block is validated. That is exactly what BIP-110 is trying to protect, not the bloat it targets.

Status, late July 2026: BIP-110 is signaling around 1% of hashrate. No major pool supports it, and Saylor, Back, and Lopp oppose it. It is unlikely to activate. We take no side in that governance fight. This page just shows we're fine either way.

Our entire on-chain footprint per payment is one 64-byte record: nf ‖ H(bundle). That is a spend marker, called a nullifier, followed by a hash of the payment data. No JPEGs, no text, no tokens stuffed into fake addresses. Just the one thing Bitcoin is uniquely good at: deciding what came first.

The good-citizen argument

OP_RETURN outputs are provably unspendable, so they never enter the UTXO set. The UTXO set is the one dataset every full node must hold in fast storage forever, and it is the cost BIP-110 is actually about. Millions of Ultraviolet transfers add zero to it. Archival nodes still keep the record transactions in block history, like any other transaction; the claim is zero UTXO-set growth, not zero bytes anywhere. Being precise about block space: an un-batched record transaction measured 186 vB on signet, published by the current stack. A vbyte is Bitcoin's fee-weighting unit, and 186 of them is roughly an ordinary payment. An earlier version of this page claimed ~10× density, which was wrong. The 64-byte payload is non-witness data, so it weighs ×4, and the transaction still needs an input and change. Batching is where density would come from: one 32-byte root covering many payments. It is designed, not yet built (spec/99 [BATCH-AVAIL]). If BIP-110's goal is lighter nodes and less junk, Ultraviolet is on its side. Our data is monetary, block-prunable, and never bloats the UTXO set.

Even if it went stricter

The 32-byte fallback

Suppose a future filter went below 64 bytes, even down to BIP-110's 34-byte cap applied to OP_RETURN. Ultraviolet still fits. Batched publication (the designed mode, spec/99 [BATCH-AVAIL]) collapses many payment records into a single 32-byte Merkle root, posted once. Measure it the same way as the 64-byte case above, as a scriptPubKey, and a 32-byte push is exactly 34 bytes of script. That is at the cap, not under it, and it puts a whole block's worth of transfers in one stamp. The protocol degrades gracefully instead of breaking. The design never assumed a generous data limit.

The one thing actually worth watching is a future semantic filter: one that bans data by what it means, not by its size. BIP-110 is a size limit, so it can't tell a spend marker from any other 64 bytes. A content filter would be a different and much harder conversation for Bitcoin to have without breaking its own neutrality.
